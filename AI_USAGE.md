# AI Usage

## My Approach

I used Claude Code to accelerate implementation, but I owned the engineering decisions throughout the project. I defined the requirements, shaped the architecture, controlled the scope, reviewed the implementation, and decided what was acceptable.

AI generated a significant portion of the initial code and subsequent implementations. My responsibility was to ensure that the output matched the project brief, followed the engineering decisions I made, handled important edge cases, and was something I could explain and defend during this assessment.

I did not treat generated code as correct simply because it compiled or passed a test. I evaluated it against the requirements, challenged questionable decisions, made changes where necessary, and verified the final behaviour before accepting it.

## Tools

| Tool | Purpose |
| --- | --- |
| **Claude Code** (agentic, in VS Code) | Scaffolding, implementation drafts, test generation, debugging assistance, running Vitest and Playwright, and checking responsive layouts. |

Claude Code was the only AI tool I used. It assisted with implementation and validation, but it did not make commits or push changes. I retained control of version control and final acceptance.

## My AI Usage Workflow

My workflow followed four stages: **Ideation → Prompting → Validation & Correctness → Acceptance.**

### 1. Ideation — I defined what needed to be built

I started with the project brief and identified the required features, technical constraints, and evaluation criteria. I considered the application structure, technology choices, visual direction, and the parts of the implementation that required particular care.

My initial direction was to build a React web application using TanStack Query and Tailwind CSS, with a feature-based folder structure and a navy blue and gold colour theme.

I also wanted the dashboard to communicate the purpose of the application clearly and present the information needed to complete the required workflows.

I did not simply accept the initial structure generated by AI. I adjusted the folder structure to better reflect how I organise and maintain React applications. This was an early example of using AI to accelerate setup while retaining ownership of the architectural decisions.

**My responsibility at this stage:** defining the requirements, setting the direction, choosing the technologies, and deciding how the application should be organised.

### 2. Prompting — I directed the implementation

I used specific prompts to move the project forward in manageable steps. Rather than leaving AI to make unrestricted decisions, I described the desired behaviour, constraints, and areas that needed attention.

My first prompt established the application foundation:

> Build a React web application with TanStack Query and Tailwind CSS, using a feature-based folder structure and a navy blue and gold colour theme. Build a dashboard that presents the project brief and provides the foundation for the required features.

After reviewing the generated structure, I made adjustments to align it with my preferred way of organising code.

As the project progressed, I refined my instructions based on what I observed in the implementation. For example, I asked AI to simplify an overengineered initial solution, use established libraries instead of unnecessary custom implementations, improve the dashboard, and revisit a pagination decision after checking the brief's stretch goals.

I also used prompts to investigate existing implementation decisions, identify missing requirements, and address specific problems rather than repeatedly rebuilding the application from scratch.

**My responsibility at this stage:** translating requirements and observations into clear instructions, narrowing the scope, and directing changes based on the needs of the project.

### 3. Validation & Correctness — I challenged the output

Generated code was a proposal, not proof of correctness.

I evaluated the implementation against the brief and the behaviour expected from a merchant-facing banking application. My validation included reviewing the code, checking calculations, running tests, exercising application flows, and inspecting responsive layouts.

I paid particular attention to:

- **Financial correctness:** amounts represented in integer kobo, correct balance calculations, idempotent transfers, and safe handling of failed requests.
- **State consistency:** ensuring a failed transfer did not overwrite a newer server balance or discard a payment received while a transfer was pending.
- **Application behaviour:** checking transfer outcomes, form validation, transaction filtering, error states, and retry behaviour.
- **Responsive design:** checking layouts at 360px and 1440px, including whether financial amounts remained readable.
- **Accessibility and usability:** reviewing keyboard navigation, contrast, and the behaviour of important interface states.
- **Test reliability:** checking that tests reflected the correct expected behaviour rather than changing application logic to satisfy an incorrect assertion.

When something looked suspicious, I investigated instead of assuming the generated implementation was right. I used concrete scenarios and calculations to determine whether the problem was in the application, the test, or the underlying approach.

For example, I questioned the use of a cached balance snapshot for rollback because restoring an old snapshot could erase a payment received during a transfer. I also checked monetary arithmetic independently when a test expected an incorrect balance.

**My responsibility at this stage:** determining whether the implementation was correct, identifying risks that ordinary happy-path tests could miss, and requiring evidence for important claims.

### 4. Acceptance — I decided what stayed

After validation, I made the final decision about whether a change met the requirements and was worth keeping.

I rejected unnecessary complexity when it made the code harder to explain or maintain. However, I did not simplify critical requirements merely to reduce the amount of code. Financial calculations, transfer idempotency, and safe rollback remained priorities even when I reduced the overall test count and replaced custom implementations with established libraries.

I also revisited earlier decisions when I discovered that they conflicted with the brief. For example, I initially requested pagination for transaction history, then reversed that decision after confirming that list virtualization was one of the stretch goals.

My acceptance criteria were straightforward:

- The implementation must satisfy the relevant project requirement.
- Critical behaviour must have meaningful tests.
- The application must work in the scenarios that matter, including failure states.
- The interface must remain usable at the target viewport sizes.
- I must understand the implementation well enough to explain its purpose and trade-offs.

I retained control of commits and pushes. AI could propose, implement, and help test a change, but it did not decide that the change was ready for submission.

**My responsibility at this stage:** deciding what to keep, what to change, what to remove, and when a feature was ready.

## Rules I Set for AI-Assisted Development

1. **Financial logic requires evidence.** Changes affecting money must have tests that would fail if the relevant behaviour broke.
2. **No autonomous commits or pushes.** I retain control of version control.
3. **Prefer established solutions where appropriate.** Use well-maintained libraries rather than reinventing functionality without a good reason.
4. **Keep the implementation explainable.** Avoid complexity that does not provide meaningful value.
5. **Validate against the brief.** A working implementation is not necessarily a complete implementation.
6. **Treat failures as part of the design.** Network errors, retries, pending transfers, and stale data must be considered, not just successful requests.

## Prompts I Gave and Decisions I Made

### 1. Establishing the application foundation

**My direction:**

> Build a React web application with TanStack Query and Tailwind CSS, using a feature-based folder structure and a navy blue and gold colour theme. Build a dashboard that presents the project brief and supports the required application features.

**What AI produced:** An initial application structure and implementation based on the project requirements.

**My decision:** I reviewed and adjusted the folder structure to align with how I organise React applications. I used the generated foundation as a starting point rather than accepting it unchanged.

### 2. Reducing unnecessary complexity

**My prompt:**

> This looks like overkill. I want to be able to defend every single line of code. Use Tailwind, use icon libraries, and use existing libraries or built tools wherever possible. One Playwright test and fewer unit tests.

**What AI produced:** A simpler implementation using Tailwind, `lucide-react`, `react-hook-form`, and `zod`. It removed custom CSS, hand-drawn icons, a custom form reducer, and URL-synchronised filters. The test suite was reduced from 84 unit tests and eight end-to-end runs to 10 unit tests and one end-to-end test.

**My decision:** I prioritised a smaller, more explainable implementation while retaining the financial logic and failure-handling behaviour central to the brief. Reducing the number of tests did not mean treating critical financial behaviour as optional.

### 3. Checking the stretch goals

**My prompt:**

> Do we have the stretch goals covered?

**What AI produced:** An audit indicating that virtualization, persisted dark mode, and retry with backoff were implemented, while Storybook was missing.

**My decision:** I requested Storybook coverage for important states, including transfer outcomes, balances during pending transfers, hostile transaction text, server failures, and lost responses.

I used this to check the completeness of the implementation against the brief, rather than relying solely on the initial feature list.

### 4. Improving the dashboard and transfer experience

**My direction:** I requested a more useful balance card, with a KYC Tier 3 indicator and money-in and money-out totals, alongside a narration dropdown with an option for custom narration.

**What AI produced:** A wider balance card containing the tier indicator and daily totals, plus predefined narration options and a custom narration field.

**My validation:** I checked that the displayed tier came from the same constant used by the Tier 3 transfer limits, rather than being an unrelated hard-coded label. I also checked the custom narration's 60-character and allowed-character rules, whether the selection survived navigating back from the review screen, and whether the mobile keyboard-only end-to-end test still passed.

### 5. Revisiting transaction history

**My initial prompt:**

> For transaction history, use pagination instead of list virtualization. Also add search and a date range instead of separate date-from and date-to fields.

**What AI produced:** Pagination with 20 items per page, search across names, narrations, and references with a 400ms debounce, and a date-range picker with presets.

**My decision:** After re-reading the brief, I realised list virtualization was one of the four stretch goals. I reversed my earlier decision and requested virtualization instead.

The final direction retained the search and date-range functionality while restoring virtualization. This demonstrated that I was willing to revise an earlier decision when it did not align with the evaluation criteria.

## Where AI Output Was Wrong or Risky

| AI output | Why it was a problem | How I addressed it |
| --- | --- | --- |
| Restoring a cached balance snapshot after a failed transfer | Could erase a payment received while the transfer was pending. | Used the server balance minus pending outbox transfers and added a regression test for the failure scenario. |
| Floating-point monetary calculations | Could introduce rounding errors and lose precision in large amounts. | Used string-based parsing and exact decimal formatting, covered by `money.test.ts`. |
| Replacing the transaction feed with a full error screen after a failed page request | Could hide previously loaded transactions when loading more failed. | Show the full error screen only when no data is available. |
| Replacing the balance with an error screen after a failed background refresh | Could hide a valid balance during a temporary network issue. | Retain the last known balance and display when it was last refreshed. |
| Date inputs causing horizontal overflow | Made the interface scroll horizontally at 360px. | Adjusted input sizing and grid columns, then checked the mobile layout. |
| Rendering `SendMoney` twice for different breakpoints | Created duplicate forms, mutations, and element IDs. | Consolidated the component into a single instance positioned with CSS grid. |
| Incorrect expected balance in an end-to-end test | The assertion was wrong even though the application's arithmetic was correct. | Recalculated the expected balance and corrected the test. |
| Incorrect Storybook mock-handler setup | Prevented the server-down scenario from loading the required mock bank list. | Corrected the MSW 2 handler setup and checked the stories in the browser. The same review identified a dark-mode contrast issue, which was fixed. |
| Balance totals breaking across lines on mobile | Could make a financial amount difficult to read. | Displayed the totals in separate rows on narrow screens and prevented amounts from wrapping. |

## What This Project Taught Me About AI-Assisted Development

AI is effective at producing a first implementation quickly, but a plausible implementation is not necessarily the correct one.

The most important part of my workflow was evaluating the output against the real requirements and considering scenarios that a generic implementation might miss. In a banking interface, that meant thinking about concurrent payments, failed transfers, monetary precision, stale data, accessibility, and the readability of financial amounts.

I also learned that using AI effectively requires knowing when to narrow the scope, when to challenge its assumptions, and when to reverse my own decisions after reviewing the brief.

**My takeaway:** AI accelerated the implementation, but I remained responsible for the requirements, technical trade-offs, validation, and final decisions. My measure of success was not how much code AI generated; it was whether the resulting application met the requirements and whether I could explain and defend the engineering decisions behind it.
